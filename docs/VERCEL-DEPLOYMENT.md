# Vercel and Supabase migration

## Status

The Vercel request entry point and PostgreSQL/Storage adapters are present. **Limited live production checks passed on 2026-11-12** at [https://returno-three.vercel.app/](https://returno-three.vercel.app/): the homepage returned HTTP 200; `/api/health` returned HTTP 200 with `service=retorno`, `version=1.3.0`, and `directImageUpload=true`; signed-out `GET /api/me` returned HTTP 401; and the deployed `app.js` contains the Keep account dialog fix. The health handler performs `SELECT 1`, so it verifies the Vercel function can reach its Postgres database and that startup succeeds. This does not validate database schema completeness, account sign-in, signup/reset email delivery, Storage uploads, production-origin upload CORS, or full administrator/student workflows. The local `npm.cmd run vercel:check` stopped at local `RETURNO_CODE_PEPPER` validation before connecting to Supabase or SMTP. It reads local `.env`, cannot inspect Vercel settings, and its local failure does not contradict the successful hosted health check. Local development defaults to SQLite; Vercel automatically selects Postgres and fails closed when `DATABASE_URL` is missing, so it cannot silently write live data to temporary SQLite storage. Previous disposable Supabase checks passed for schema/RLS/bucket settings, synthetic report flows, private image operations, outcome-proof review/cleanup, and localhost CORS. Live signup email, shared rate-limit concurrency, production-origin image CORS, and full production workflows remain unverified.

The selected target is Vercel Hobby with Supabase Postgres and Supabase Storage. Existing local SQLite remains the development and test backend. Supabase SQL migrations `001`–`004` must all be applied before the deployment check passes. Migration `004-outcome-notification-proof.sql` adds the private proof reference used by the current student outcome request flow.

The recommended Supabase region for RETURNO's Philippine testers is Southeast Asia (Singapore, `ap-southeast-1`); `vercel.json` pins the function to Vercel's matching Singapore region (`sin1`) to reduce database round-trip latency. Keep both regions aligned if the database region changes. The Postgres pool uses Vercel's idle-connection lifecycle hook, and password-reset and password-change emails use Vercel's `waitUntil()` integration so the function can manage database connections and finish mail tasks after a response. This does not make SMTP or a misconfigured deployment succeed by itself.

## Migration phases

1. **Vercel request boundary (complete):** Vercel routes `/api/*` to `api/index.js`, which exports the same request handler used by the local Node server. Local startup behavior remains unchanged. The platform adapter does not start a separate listener.
2. **Postgres persistence (implemented; final provider checks outstanding):** the parameterized Postgres adapter supports request-scoped transactions and awaits database operations. Email delivery cooldowns use shared Postgres records. The admin setup and password-recovery commands now await Postgres operations, load `.env`, and close their connection pool. Server connections use Supabase's transaction pooler and verified TLS. If certificate verification fails, set `DATABASE_SSL_CA_FILE` locally or the PEM-valued `DATABASE_SSL_CA` in the host environment using Supabase's root CA. Keep certificate verification enabled. Remove `sslmode`, `sslcert`, `sslkey`, and `sslrootcert` from `DATABASE_URL` when supplying TLS options; see [node-postgres TLS guidance](https://node-postgres.com/features/ssl). Apply migrations `001-retorno-schema.sql`, `002-distributed-rate-limits.sql`, `003-email-delivery-reservations.sql`, and `004-outcome-notification-proof.sql` in order.
3. **Private image storage (report flow smoke-tested; outcome proof and production origin outstanding):** in Postgres mode, the server issues short-lived, path-scoped upload grants; the browser uploads directly to the private bucket, and the server downloads, decodes, validates, resizes, strips metadata and authorizes objects before linking them to a report or outcome request. Report images use an authenticated same-origin endpoint; outcome proof uses an admin-only endpoint and is deleted when reviewed or dismissed. Report image upload/retrieval/replacement/deletion and localhost CORS passed. The disposable-project smoke test passed outcome-proof upload, admin-only retrieval, approval and deletion. Verify the same workflow and CORS from the real Vercel preview before inviting testers. Direct upload avoids Vercel Functions' 4.5 MB request/response limit while preserving RETURNO's 10 MB image cap. See [Vercel Function limits](https://vercel.com/docs/functions/limitations) and [Supabase signed upload documentation](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl). Keep the elevated key server-side only.
4. **Shared rate limiting (implementation scaffolded, provider integration outstanding):** Postgres mode now stores HMAC-address keys and counters in a bounded table and updates them under a transaction-scoped advisory lock; local SQLite retains the bounded in-memory limiter. Vercel supplies an overwritten `X-Forwarded-For` client-IP header to prevent spoofing; see [Vercel request headers](https://vercel.com/docs/headers/request-headers). Rate keys use the stable `RETURNO_CODE_PEPPER`, and expired rows are pruned on sensitive requests. The pepper must be a stable server-side Vercel secret before readiness can be enabled. Verify concurrent behavior against a disposable Supabase Postgres project. The privacy notice and operational retention details should account for this pseudonymous security data before public use.
5. **Deployment verification:** set server-only environment values in Vercel (`DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_SECRET_KEY` or legacy service-role key, `SUPABASE_STORAGE_BUCKET`, stable `RETURNO_CODE_PEPPER`, `COOKIE_SECURE=true`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, and `MAIL_FROM`). Set `COOKIE_SECURE` to exactly `true` for Production (and Preview when testing); the API refuses production requests if it is missing or false. Vercel provisions HTTPS/TLS for deployment domains. After saving an environment variable, redeploy so the deployment receives it. Verify by signing in over `https://` and checking the browser's stored `retorno_session` cookie has Secure, HttpOnly, and SameSite=Strict enabled. Never expose database or Storage credentials to browser code. Do not import local accounts or reports until a separate backup/export and data-migration plan is reviewed.

## Readiness checklist

1. In a disposable Supabase project, apply all four files in `migrations/postgres/` in numeric order. `npm run vercel:check` performs a read-only metadata check for tables, RLS and revoked browser-role reads, the private 10 MB image bucket, TLS connection, SMTP authentication and required local deployment settings, including server-only Storage key format. It never prints secret values or account/report records. It does not change the readiness flag.
2. Create the first administrator against the same Postgres database with `npm run admin`; the command now loads the project's `.env`. Confirm login and then use `npm run admin:reset` to verify password updates also revoke sessions. Do not pass passwords in command-line arguments or environment variables.
3. Run `npm run supabase:smoke` using a disposable project and valid server-only key. It exercises student/admin login, report creation, direct proof upload, admin-only retrieval, approval and cleanup. Then verify registration email, password reset, report replacement/deletion, shared rate limiting and email reservations with isolated synthetic records; clean up test accounts and Storage objects afterward.
4. Import the GitHub repository into Vercel. Keep the Root Directory as the repository root, Framework Preset as Other, and output directory as `public`; use Node **24.x**. Add the environment variables listed below to Preview. Vercel automatically uses Postgres; no readiness toggle is required. Deploy Preview and verify `/api/health`, student/admin permissions, signup email, private image upload, outcome proof review/cleanup, and admin setup against that Preview URL. Never put the Supabase elevated key in a `NEXT_PUBLIC_*` variable.
5. After Preview checks pass, add the same server-side configuration to Production, deploy Production, and repeat health, login, email, image, and admin-review checks. Only then share the link.

## Current behavior and safety

- `api/index.js` exports the Node handler expected by Vercel.
- The Vercel entry point loads the shared handler on demand. Initialization failures return a sanitized JSON 503 with an incident ID; Vercel runtime logs contain only the error class/code and matching incident ID, not exception messages or connection credentials. Unexpected request failures also return a generic 500 with a correlatable incident ID; runtime logs omit database/provider exception text. Local development retains detailed error logs.
- `vercel.json` serves the existing `public/` directory and routes API requests to that function.
- In Postgres mode, `/api/health` reports that direct image uploads are enabled. The browser obtains a server-issued upload grant and sends the file directly to Supabase; the service-role key remains server-side. In local SQLite mode, the existing data-URL upload route remains active.
- Vercel automatically selects Postgres. If `DATABASE_URL` is absent, initialization fails with a safe diagnostic; it never falls back to SQLite. Local SQLite remains the default outside Vercel.
- Set `RETURNO_DATABASE=postgres` only for local testing with a disposable Postgres database. No manual readiness flag is needed.
- Local `.env` values do not transfer to Vercel; enter production values through Vercel's Environment Variables settings. SMTP delivery has not been verified.
- Email send cooldown coordination is database-backed in Postgres mode. Apply `003-email-delivery-reservations.sql` and verify signup/reset behavior against a disposable Supabase project before enabling Vercel. Password-reset delivery and password-change security notices are registered with Vercel's background-task lifecycle. Signup verification remains awaited as part of registration so the API can handle delivery failure before creating a session.
- Supabase Free projects may pause after a week of low activity. Free quotas and eligibility must be checked in the provider dashboards before inviting users.

The live check above verifies the deployed frontend, function startup, Postgres connectivity, and signed-out API behavior only. To complete production verification, check sign-in, signup/reset email, report image upload/retrieval, outcome-proof review, and administrator workflows with approved synthetic accounts. A local `vercel:check` result only validates local settings and Supabase/SMTP connectivity; it does not prove that Vercel has matching environment variables or that the deployed function is healthy.
