# Vercel and Supabase migration

## Status

The Vercel request entry point and partial PostgreSQL/Storage adapters are present. **RETURNO is not deployable to Vercel yet.** Local development still defaults to SQLite, and the live Supabase check has only verified schema presence/RLS and bucket settings; application flows have not been integration-tested. Startup deliberately fails unless the explicit readiness flag is enabled, so an incomplete deployment cannot silently accept accounts or reports into ephemeral storage.

The selected target is Vercel Hobby with Supabase Postgres and Supabase Storage. Existing local SQLite remains the development and test backend during migration. A disposable Supabase test project has been configured and the user reports applying all three SQL migrations; live schema and application integration checks remain outstanding.

## Migration phases

1. **Vercel request boundary (complete):** Vercel routes `/api/*` to `api/index.js`, which exports the same request handler used by the local Node server. Local startup behavior remains unchanged. The platform adapter does not start a separate listener.
2. **Postgres persistence (implementation scaffolded, provider integration outstanding):** added a parameterized Postgres adapter, request-scoped transactions, placeholder/SQLite SQL translation, and a Supabase schema for the current tables and cascades. The API awaits DB operations for asynchronous Postgres I/O. Email delivery cooldowns now reserve signup sends with a shared Postgres key and reserve reset codes with a conditional upsert, preventing simultaneous instances from replacing one another's codes. Migration `003-email-delivery-reservations.sql` adds the server-only signup reservation table. The user reports running all three migrations in the disposable project; independent schema verification and application integration tests remain outstanding. Server connections use Supabase's transaction pooler and verified TLS. If certificate verification fails, set `DATABASE_SSL_CA_FILE` locally or the PEM-valued `DATABASE_SSL_CA` in the host environment using the root CA from Supabase Dashboard → Database → Settings → SSL Configuration. Keep `rejectUnauthorized` enabled. When CA options are supplied in code, remove `sslmode`, `sslcert`, `sslkey`, and `sslrootcert` from `DATABASE_URL`, since node-postgres may replace the TLS object when those URL parameters are present; see [node-postgres TLS guidance](https://node-postgres.com/features/ssl). Apply migrations `001-retorno-schema.sql`, `002-distributed-rate-limits.sql`, and `003-email-delivery-reservations.sql` in order. Preserve all existing student/admin permissions and cascades. Add isolated integration tests against a disposable Postgres schema before enabling Vercel.
3. **Private image storage (client/server flow implemented, provider integration outstanding):** in Postgres mode, the authenticated server issues a short-lived, path-scoped Supabase Storage upload grant; the browser uploads directly to the private bucket, then the server downloads, decodes, validates, resizes, strips metadata, and authorizes the object before attaching its key to a report. Report image bytes now load through an authenticated same-origin endpoint. Post/account deletion and image replacement trigger best-effort object cleanup. Vercel Functions limit request and response bodies to 4.5 MB, below RETURNO's 10 MB image cap, so this avoids sending image bytes through the function. See [Vercel Function limits](https://vercel.com/docs/functions/limitations) and [Supabase signed upload documentation](https://supabase.com/docs/reference/javascript/storage-from-createsigneduploadurl). The bucket must be private and capped at 10 MB; no service-role secret is sent to the browser. Configure the bucket/schema and verify CORS, signed upload, validation, authenticated retrieval, and cleanup against a disposable Supabase project before enabling deployment.
4. **Shared rate limiting (implementation scaffolded, provider integration outstanding):** Postgres mode now stores HMAC-address keys and counters in a bounded table and updates them under a transaction-scoped advisory lock; local SQLite retains the bounded in-memory limiter. Vercel supplies an overwritten `X-Forwarded-For` client-IP header to prevent spoofing; see [Vercel request headers](https://vercel.com/docs/headers/request-headers). Rate keys use the stable `RETURNO_CODE_PEPPER`, and expired rows are pruned on sensitive requests. The pepper must be a stable server-side Vercel secret before readiness can be enabled. Verify concurrent behavior against a disposable Supabase Postgres project. The privacy notice and operational retention details should account for this pseudonymous security data before public use.
5. **Deployment verification:** set only server-side Supabase secrets in Vercel, apply all three schema migrations to a disposable project, verify registration/login/email, report CRUD and image flows, and run Postgres integration tests before deploying a test environment. Set `RETURNO_POSTGRES_READY=true` only after those checks, configure shared rate limiting and secure cookies, then deploy a test environment. Do not import current local accounts or reports until a separate backup/export and data-migration plan is reviewed.

## Current behavior and safety

- `api/index.js` exports the Node handler expected by Vercel.
- `vercel.json` serves the existing `public/` directory and routes API requests to that function.
- In Postgres mode, `/api/health` reports that direct image uploads are enabled. The browser obtains a server-issued upload grant and sends the file directly to Supabase; the service-role key remains server-side. In local SQLite mode, the existing data-URL upload route remains active.
- Vercel startup refuses to initialize unless `RETURNO_POSTGRES_READY=true`; leave it unset until real Postgres/Storage integration tests and production security configuration are complete. The local SQLite backend is still the default outside Vercel.
- Set `RETURNO_DATABASE=postgres` only for local testing with a disposable Postgres database. Vercel requires `RETURNO_POSTGRES_READY=true`; do not set this flag yet because real provider integration and full deployment verification remain incomplete.
- SMTP configuration and secure-cookie settings still need production environment values; no secrets belong in Git.
- Email send cooldown coordination is database-backed in Postgres mode. Apply `003-email-delivery-reservations.sql` and verify signup/reset behavior against a disposable Supabase project before enabling Vercel.
- Supabase Free projects may pause after a week of low activity. Free quotas and eligibility must be checked in the provider dashboards before inviting users.

This scaffold is not evidence of a successful Vercel build or deployment. The next phase is applying all three migrations to a disposable Supabase project and adding real Postgres/Storage integration tests.
